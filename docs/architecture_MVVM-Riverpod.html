Architecture: MVVM + Riverpod State Management

Tài liệu mô tả kiến trúc MVVM cho dự án Flutter: các lớp View, ViewModel, Domain, Repository, Service; cấu trúc thư mục theo lớp, luồng state, ưu/nhược điểm, cách test và quy ước làm việc.

1. Tổng quan

Tài liệu về kiến trúc và state của ứng dụng Flutter: áp dụng mô hình MVVM (View – ViewModel – Model), thư mục tổ chức theo từng lớp của MVVM, quản lý state và dependency injection bằng Riverpod. Trong đó Notifier của Riverpod đóng vai trò ViewModel.

Trạng thái source base: Product hiện mới có Domain model, repository contract và use case; chưa có Data implementation/service hay luồng UI catalog hoàn chỉnh. Các service platform đang dùng (như SharedPreferences, FCM và device info) hiện nằm trong app/core/services/. User hiện được khai báo trong Domain nhưng vẫn có JSON serialization và được lưu trực tiếp qua SharedPreferences; đây là phần chưa hoàn toàn theo ranh giới mục tiêu — khi hoàn thiện persistence, chuyển serialization/mapping sang Data và giữ Domain model thuần. Với feature mới có API hoặc storage riêng, đặt adapter/service của feature trong data/ để Repository implementation điều phối. Cây trên phản ánh code hiện tại, không phải danh sách file bắt buộc cho mọi feature.

2.2 Tổ chức thư mục theo lớp MVVM

  • Thư mục cấp cao nhất phản ánh đúng các lớp của kiến trúc: presentation/ (View + ViewModel), domain/ (Repository interface, Model), data/ (Repository implementation, Service, DTO).
  • presentation/ là Presentation layer: mỗi màn hình có một thư mục riêng, bên trong chia theo vai trò views/, view_models/, widgets/. Mỗi màn hình sở hữu View (page), ViewModel (Notifier) và UI state (Freezed).
  • data/ là Data layer: Repository implementation, DTO và adapter/service theo feature để giao tiếp với API hoặc nguồn lưu trữ.
  • Service: service gắn với nguồn dữ liệu của một feature nên đặt trong data/services/remote/ hoặc data/services/local/ (ví dụ <feature>_api_service.dart). Plugin/platform service dùng chung, không thuộc riêng feature, có thể đặt trong app/core/services/; Repository implementation gọi service này hoặc adapter Data. Class Service dùng hậu tố Service.
  • domain/ chứa Repository contract, model nghiệp vụ và các Use Case khi thực sự cần. ViewModel có thể gọi Repository trực tiếp với thao tác đơn giản; dùng Use Case khi cần phối hợp nhiều Repository, logic nghiệp vụ phức tạp hoặc logic được nhiều ViewModel dùng lại. Nếu dự án chọn Domain contract, Use Case phụ thuộc contract và implementation nằm ở data/repositories/.
  • app/ là hạ tầng dùng chung (network, storage, router, language), không chứa nghiệp vụ feature. Trong source hiện tại, SharedPreferences/FCM/device-info plugin services đang ở app/core/services/; đây là hạ tầng platform dùng chung, không phải API để ViewModel gọi trực tiếp. Widget dùng chung đặt ở presentation/widgets/.
  • State ngắn hạn chỉ phục vụ một widget thì để tại widget (useState / StatefulWidget), không cần đưa hết lên ViewModel.

2.4 Cấu trúc gợi ý của một màn hình

Mỗi màn hình gồm 3 file chính (View, ViewModel, State), ví dụ với home:

presentation/home/
├── views/
│   └── home_page.dart         # View: vẽ UI theo state, chuyển sự kiện sang ViewModel
├── view_models/
│   ├── home_view_model.dart   # ViewModel (Notifier): logic trình bày, gọi Repository
│   └── home_state.dart        # UI state (Freezed, bất biến)
└── widgets/                   # (tùy chọn) widget riêng của màn hình

Nếu màn hình lớn, thêm thư mục widgets/ để chứa widget riêng của màn hình. Page đơn giản không có logic (ví dụ splash_page.dart, onboarding_page.dart) chỉ cần View, không bắt buộc có ViewModel.

Repository contract đặt trong domain/repositories/, implementation trong data/repositories/, Service/adapter theo feature trong data/services/. Ví dụ feature có API: domain/repositories/auth_repository.dart, data/repositories/auth_repository_impl.dart, data/services/remote/auth_api_service.dart. Platform service dùng chung có thể được cung cấp từ app/core/services/.

Quy ước đặt tên file và class

  • Tên file Dart dùng lower_snake_case.dart; tên class dùng UpperCamelCase. Tên nên mô tả feature hoặc tác vụ cụ thể, tránh tên chung như app_repository.dart nếu Repository chỉ xử lý một capability.
  • Presentation: <feature>_page.dart / <Feature>Page; <feature>_view_model.dart / <Feature>ViewModel; <feature>_state.dart / <Feature>State. Action của ViewModel dùng động từ rõ nghĩa như loadProducts(), skipUpdate().
  • Domain Repository contract: <capability>_repository.dart / <Capability>Repository. Use Case: <verb>_<object>_use_case.dart / <Verb><Object>UseCase, ví dụ get_products_use_case.dart / GetProductsUseCase hoặc skip_update_use_case.dart / SkipUpdateUseCase.
  • Data implementation luôn giữ cùng capability với contract và thêm hậu tố _impl: product_repository_impl.dart / ProductRepositoryImpl, app_update_repository_impl.dart / AppUpdateRepositoryImpl.
  • Model trong data/models/ phản ánh payload của nguồn dữ liệu, đặt tên file theo mẫu <feature>_request.dart hoặc <feature>_response.dart; class tương ứng phải dùng hậu tố Request/Response (vd: product_response.dart / ProductResponse). Request/response chỉ chứa cấu trúc dữ liệu trao đổi và serialize/deserialize; mapping sang model nghiệp vụ do Data/Repository thực hiện.
  • Model trong domain/models/ là model nghiệp vụ dùng giữa Repository và Presentation/UI, đặt tên theo khái niệm nghiệp vụ thuần, không thêm hậu tố Request, Response hay Dto (vd: product.dart / Product).
  • Service dùng tên tác vụ/nguồn dữ liệu có hậu tố Service, ví dụ product_catalog_service.dart / ProductCatalogService.
  • Model chỉ phục vụ giao diện (ví dụ nội dung toast) thuộc presentation/, không đưa vào Domain hoặc Data. Model serialize/deserialize cho SharedPreferences/local database vẫn thuộc Data vì gắn với định dạng lưu trữ.
  • Provider dùng tên dependency cộng hậu tố Provider; khi có nhiều loại dependency thì giữ rõ vai trò, ví dụ getProductsUseCaseProvider và productRepositoryProvider.
  • Test phản chiếu tên và thư mục của đối tượng: ví dụ đang có skip_update_use_case_test.dart, app_update_repository_impl_test.dart và app_shell_view_model_test.dart. Fake/Mock thêm tiền tố Fake/Mock theo contract được implement.

2.5 Quy tắc phụ thuộc

Phụ thuộc đi một chiều; Use Case là tùy chọn: View → ViewModel → (Use Case) → Domain Repository contract ← Data Repository implementation → Service. Với thao tác đơn giản, ViewModel có thể gọi Repository contract trực tiếp. Provider trong app/providers/ ghép contract với implementation. Dữ liệu quay lại UI qua state; event/command từ UI đi theo chiều ngược lại.

  • View chỉ dùng ViewModel/State của chính màn hình và widget chung ở presentation/widgets.
  • ViewModel chỉ lấy dữ liệu qua Repository (hoặc Use case) bằng provider; không gọi Service trực tiếp.
  • app/core và data không import ngược presentation; domain không import presentation và data.
  • Màn hình không gọi chéo trực tiếp vào ViewModel/state của màn hình khác; nếu cần dùng chung, đưa xuống Repository/Use case ở data/ hoặc domain/, hoặc provider dùng chung ở app/.
  • Repository và Service được khai báo thành provider để dễ override bằng fake khi test.
  • Generated file (*.g.dart, *.freezed.dart) không sửa tay.

Đối chiếu với Flutter app architecture guide

Source base này tham khảo Flutter app architecture guide. Các nguyên tắc tương đồng gồm tách View và ViewModel, luồng dữ liệu một chiều, UI là hàm của state bất biến, Repository làm source of truth, và Service cô lập API/platform plugin. Flutter guide mô tả UI layer và Data layer là cấu trúc nền tảng; Domain/Use Case là lớp tùy chọn, không phải yêu cầu cho mọi feature.

  • Trong source base, Repository contract được tách vào domain/repositories/ và implementation đặt ở data/repositories/ để biểu đạt dependency inversion và cho phép override provider trong test.
  • ViewModel gọi Repository trực tiếp khi action đơn giản. Thêm Use Case khi cần phối hợp nhiều Repository, xử lý logic nghiệp vụ phức tạp hoặc chia sẻ logic giữa các ViewModel; tránh tạo Use Case chỉ để chuyển tiếp một method.
  • Repository chịu trách nhiệm dữ liệu và điều phối service/cache/error handling phù hợp; không để Repository biết ViewModel hoặc phụ thuộc Repository khác. Nếu cần phối hợp nhiều nguồn nghiệp vụ, đặt orchestration ở Use Case hoặc ViewModel tùy độ phức tạp.
  • Các service plugin dùng chung hiện còn ở app/core/services/; với feature mới, service của nguồn dữ liệu nên được tổ chức trong data/services/. Đây là quy ước tổ chức của source base, không phải yêu cầu bắt buộc của Flutter guide.

Luồng thực tế trong source: bỏ qua nhắc cập nhật

Đây là luồng minh họa hiện nối View → ViewModel → Use Case → Repository → local storage trong source base. Flutter guide cho phép ViewModel gọi Repository trực tiếp nếu logic đơn giản; Use Case ở ví dụ này được giữ để thể hiện cấu trúc Domain của source base. Thao tác chỉ lưu lựa chọn cục bộ, không gọi server:

  1. View presentation/shell/widgets/modal_update_app.dart gửi action skipUpdate() đến AppShellViewModel.
  2. AppShellViewModel gọi skipUpdateUseCaseProvider từ app/providers/app_providers.dart, chờ hoàn tất rồi cập nhật UI state doNotShowAgain.
  3. SkipUpdateUseCase gọi contract AppUpdateRepository.skipUpdate() trong domain/.
  4. Provider composition cung cấp AppUpdateRepositoryImpl trong data/; implementation ghi thời điểm bỏ qua vào PrefsLocalStorage thuộc app/core/services/.
  5. Kết quả bất đồng bộ quay về ViewModel, sau đó state mới làm View cập nhật.
ModalUpdateApp
  → AppShellViewModel.skipUpdate()
  → skipUpdateUseCaseProvider
  → SkipUpdateUseCase
  → AppUpdateRepository (Domain contract)
  ← AppUpdateRepositoryImpl (Data implementation)
  → PrefsLocalStorage.skipUpdate()
  → cập nhật AppShellState.doNotShowAgain

Các phần chưa thành luồng hoàn chỉnh: Product mới có model, contract và use case, chưa có repository implementation, service hoặc UI catalog. AppVersionResponse và Domain AppVersion đã tách riêng nhưng chưa có API/repository/mapping; AppShellViewModel.checkVersion() hiện vẫn là stub.

5. Ưu điểm

  • Tách trách nhiệm rõ: View chỉ vẽ, ViewModel giữ logic trình bày, Repository lo dữ liệu, Service lo giao tiếp thô.
  • State tập trung, luồng cập nhật một chiều; UI phản ứng theo provider.
  • Scalability: các lớp độc lập, thêm màn hình mới chỉ thêm thư mục trong presentation/ và tái sử dụng Repository có sẵn.
  • Testability: test ViewModel chỉ cần fake Repository; test Repository chỉ cần fake Service; không cần dựng UI.
  • Nguồn dữ liệu duy nhất: đổi API, thêm cache hoặc đổi local storage chỉ sửa ở Repository, không ảnh hưởng ViewModel/View.
  • Type safety + giảm boilerplate nhờ code generation (Riverpod, Freezed, Retrofit).
  • Dễ phân chia việc trong team: tách người làm UI (presentation/) và người làm dữ liệu (data/), hoặc chia theo màn hình.
  • Dễ onboarding: nhìn thư mục (presentation, domain, data) và hậu tố file (_page, _view_model, _state, _repository, _repository_impl, _use_case) là biết vai trò.

6. Nhược điểm

  • Ranh giới giữa các lớp không bị ép buộc: View vẫn có thể gọi thẳng Repository/Service hoặc ViewModel vẫn có thể dùng BuildContext, khiến kiến trúc bị rò rỉ dần nếu không kiểm soát khi review.

8. Test (Unit test + Widget test)

Quy định: mỗi feature bắt buộc có Unit test cho logic (ViewModel, Repository) và Widget test cho UI (View). Đưa flutter test vào CI để bắt lỗi trước khi merge. Integration test là tùy chọn, chỉ cho các luồng chính.

Quy ước đặt file test

Source base yêu cầu viết unit test cho ViewModel và Repository, widget test cho View. File test nằm trong thư mục test/ ở gốc project (ngang hàng lib/), tên file kết thúc bằng _test.dart. Các file test phản chiếu cấu trúc lib/.

9.5 Local storage với SharedPreferences

SharedPreferences lưu dữ liệu key-value nhỏ: thông tin công ty và phiên đăng nhập. Truy cập qua AuthLocalService (Service local), chỉ Repository được gọi; ViewModel và View không đọc/ghi trực tiếp.

Bảo mật khi publish lên store (tùy chọn theo dự án)

SharedPreferences lưu dữ liệu dạng văn bản thường, không mã hóa; trên thiết bị đã root/jailbreak hoặc qua bản backup, dữ liệu có thể bị đọc. Mức bảo mật cần thiết tùy vào từng dự án (loại dữ liệu, yêu cầu của khách hàng), nên có hai phương án để lựa chọn:

Phương ánCách lưuƯu điểmNhược điểmPhù hợp khi
A. Chỉ SharedPreferencesToàn bộ company, token và thông tin nhân viên lưu trong SharedPreferencesĐơn giản, ít thư viện, đọc/ghi nhanhKhông mã hóa; token có thể bị lấy trên máy root/jailbreak hoặc từ backupApp nội bộ hoặc dữ liệu không nhạy cảm, token ngắn hạn

9.6 Local database với Hive

Hive dùng cho dữ liệu nghiệp vụ cần lưu local (cache, dùng offline), thay cho SQLite: dữ liệu chia theo box (tương đương bảng), mỗi bản ghi có key. Phân vai: SharedPreferences cho cấu hình/phiên đăng nhập nhỏ, Hive cho dữ liệu dạng danh sách/bản ghi.

Cấu trúc thư mục

lib/data/
├── models/local/                   # Model lưu trong Hive (@HiveType)
│   └── employee_hive.dart
└── services/local/
    ├── auth_local_service.dart     # SharedPreferences
    └── hive/
        ├── hive_boxes.dart         # Tên box (hằng số)
        ├── hive_service.dart       # Khởi tạo, đăng ký adapter, mở box
        └── employee_local_service.dart  # Truy cập box employee
  • Khởi tạo HiveService.init() một lần ở bootstrap, trước runApp.
  • Chỉ Repository gọi Service Hive; Repository quyết định đọc cache hay gọi API. ViewModel và View không biết Hive.
  • Model Hive tách riêng với DTO và model của app; Repository map qua lại.
  • Khi logout: xóa các box chứa dữ liệu theo người dùng (employee_box), giữ cấu hình chung.
  • Dữ liệu nhạy cảm: mở box có mã hóa (HiveAesCipher) với khóa lưu ở secure storage.
  • Test: đưa Service Hive sau interface và dùng fake trong test/fakes/ như các Service khác.
